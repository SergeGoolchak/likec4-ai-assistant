# Как расширять существующую модель, не создавая дубликатов

Ключевой принцип системы: дополнять существующую архитектуру, а не описывать её заново (ФТ7). Практические правила при работе с LikeC4-кодом:

1. **Всегда сначала искать существующий элемент** с тем же или близким по смыслу назначением (по title, kind, description, связям), прежде чем создавать новый. Разные формулировки в аналитической спецификации ("Order Service", "сервис заказов", "orders-service") с высокой вероятностью указывают на один и тот же существующий элемент.
2. **Новый элемент — только если после проверки соответствующего элемента действительно нет.** Если есть сомнение — это повод для вопроса пользователю (см. Ambiguity Detection), а не для тихого решения в любую сторону.
3. **Изменение существующего элемента — через `extend`**, не через повторное объявление с тем же id (это приведёт к ошибке дублирующегося идентификатора) и не через копирование блока элемента с изменениями в новый файл.
4. **Новые элементы добавляются в файл, логически соответствующий существующей структуре проекта** (например, если у проекта уже есть файл `services/orders.c4` с сервисами домена заказов — новый сервис того же домена уместнее туда, а не в отдельный новый файл).
5. **Naming conventions существующего проекта имеют приоритет над общими рекомендациями.** Если в проекте уже сложился стиль именования id (`camelCase`, `kebab-case`, с префиксом домена и т.п.) — новый элемент должен следовать этому стилю, а не абстрактно "правильному" стилю из общих знаний.
