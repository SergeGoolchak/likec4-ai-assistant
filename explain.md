# Пояснения по ходу реализации

Этот файл — журнal объяснений: почему решения приняты именно так, какие риски видны, какие отходы от [плана](./docs/development-plan.md) сделаны и почему, что дальше. Обновляется по ходу реализации каждого milestone.

---

## Milestone 0 — Foundation & Scaffolding

### Технологические решения и почему именно так

**npm workspaces, а не pnpm/yarn.**
Node 24 и npm 11 уже установлены на машине, workspaces встроены в npm с 7-й версии — не нужна дополнительная зависимость менеджера пакетов. Для монорепо на 15-20 пакетов (весь набор из плана) этого достаточно; pnpm дал бы более строгий граф симлинков, но это не критично на этом масштабе.

**ESM (`"type": "module"`) везде.**
Экосистема `likec4` (построена на Langium) публикуется как ESM-first — подтвердилось при проверке реального пакета (`npm view likec4 exports`): все экспорты идут через `.mjs`/`import`, без `.cjs`/`require`. Если бы мы начали с CommonJS, при интеграции `likec4-adapter` в Milestone 1 пришлось бы либо мигрировать весь монорепо на ESM задним числом, либо городить interop-костыли (`await import()`, `esModuleInterop` edge cases). Заложили ESM с первого коммита, чтобы не переписывать.

**`tsx` вместо предварительной компиляции `tsc` для запуска сервера — и в dev, и в `npm start`.**
Сознательное упрощение относительно "стандартного" продакшен pipeline с TS project references и раздельной сборкой пакетов в правильном топологическом порядке. Для локального инструмента (не публикуемого npm-пакета, не деплоящегося в контейнер) это избыточная сложность на старте. `tsx` — обёртка над esbuild, транспилирует на лету с минимальными накладными расходами, этого достаточно для локального MVP.
*Компромисс:* пакеты типа `core-domain`/`secrets` не собираются в `dist/`, а импортируются как raw `.ts` через `"main"/"types"` в `package.json`, указывающие прямо на `src/index.ts`. Это работает, пока весь граф потребителей тоже идёт через `tsx`/Vite (которые сами транспилируют TS). Если в будущем понадобится настоящая дистрибуция (например, упаковка в installer) — здесь потребуется вернуться и добавить нормальный build step.

**`noUncheckedIndexedAccess: true` в базовом tsconfig.**
Не было явно в плане, добавил сам. Даёт compile-time проверку на то, что `Map.get()`/`array[i]` могут вернуть `undefined` — критично для кода вроде `ArchitectureGraph.neighborsIndex.get(id)`, где забытая проверка на `undefined` обычно всплывает не сразу, а как runtime-краш посреди AI pipeline на сессии пользователя. Cтрогость окупается именно в доменно-модельном коде такого объёма.

**SecretsVault: зашифрованный локальный файл (AES-256-GCM), ключ — в отдельной директории от данных.**
Это прямая реализация fallback-варианта из риска №5 плана ("не хранить ключ шифрования рядом с зашифрованными данными открытым текстом"). Конкретно: секреты — `~/.likec4-ai/secrets.enc`, ключ — `~/.likec4-ai-key/vault.key` (разные поддеревья `$HOME`, права `0600`/`0700`). Это защищает от случайного чтения одного из двух файлов в отрыве от другого, но **не** от атакующего с полным доступом к диску — честно задокументировано в комментарии в коде как известное ограничение MVP. Апгрейд на OS keychain — следующий логичный шаг, не требующий менять код, использующий порт `SecretsVault` (только реализацию за портом).
Проверено 4 юнит-тестами: секрет читается/пишется/удаляется, значение не встречается в открытом виде на диске, ключ и данные физически в разных файлах.

**Раздельные technical/user-facing логгеры с первого коммита.**
Technical-логгер (`pino`) настроен с `redact` по путям вида `*.apiKey`, `*.token`, `*.pat`, `headers.authorization` — то есть маскирование секретов встроено в саму точку логирования, а не полагается на то, что каждый вызывающий код не забудет сам всё вычистить. User-facing логгер — отдельный инстанс без технического шума; с Milestone 5 события из него дополнительно лягут в `SessionRecord.userFacingTimeline` для экрана History.

**Карточный UI с success/error состояниями уже в Milestone 0**, хотя по факту экран пока показывает только health-check backend.
Причина: визуальный язык ФТ29 ("карточная структура, понятные success/warning/error states") — это системное решение, которое дешевле сразу delать правильно (Tailwind + паттерн карточки с точкой-индикатором статуса), чем воспроизводить в Milestone 11, когда экранов будет уже полтора десятка.

### Обнаруженные риски / находки

**`@fastify/static@8.3.0` — 4 уязвимости (path traversal / authorization bypass), обнаружено при `npm install`.**
Изначально в плане/скаффолде была версия `^8.0.0`. `npm audit` сразу после установки показал high severity advisories, актуальные для всей линейки вплоть до `10.1.1`, исправлено в `10.1.2+`. Обновил зависимость на `^10.1.3` (та же мажорная линия под Fastify v5, просто более новый патч) — `npm audit` стал чист (0 уязвимостей). Это отход от изначально написанной версии в package.json, но не от архитектурного решения — просто исправление конкретного номера версии по факту публикации CVE.

**Реальность пакета `likec4@1.59.3` (проверено `npm view`) — подтверждает ключевые архитектурные ставки плана:**
- Пакет существует, публикуется как чистый ESM (`.mjs`) — подтверждает решение по ESM выше.
- Есть отдельный `./react` export — подтверждает, что план "переиспользовать официальный React-компонент для рендеринга диаграмм" (вместо своего SVG-рендерера) реалистичен.
- Есть `./model` и `./model/builder` exports — вероятный кандидат на программный API, который понадобится `LikeC4Parser`/`LikeC4Validator` в Milestone 1.
- **Новая находка, которой не было в плане:** CLI-пакет (`bin: likec4`) тянет `playwright` в зависимостях. Похоже, экспорт диаграмм в PNG/SVG через CLI идёт через headless-браузер. Для нашего сценария (Node-процесс, который должен быть лёгким и запускаться локальным `npm start` без доп. шагов) поднимать headless Chromium внутри собственного backend — заметный вес и сложность (загрузка браузерных бинарников при `npm install`, время холодного старта). Это усиливает аргумент в пользу приоритета "живого" `./react`-компонента для Preview (Milestone 10) вместо серверного CLI-экспорта как первого варианта, а не просто fallback-запасного.

### Что не стал делать сейчас (и почему это не отход от плана, а его буквальное соблюдение)

Не создавал пустые директории/пакеты для `architecture-graph`, `change-engine`, `context-builder`, `likec4-adapter`, `llm-openai`, `llm-local`, `confluence-adapter`, `repo-local-adapter`, `repo-bitbucket-adapter`, `knowledge-global`, `knowledge-project`, `documentation-engine`, `persistence`, `ui-kit`, хотя в плане они перечислены общим списком структуры. План описывает *целевую* структуру монорепо, а не то, что должно физически существовать с Milestone 0. Заведение пустых пакетов без реального содержимого — это структура ради структуры (мёртвый код, который не за что зацепиться тестами). Каждый пакет появится в тот milestone, где для него есть первая реальная реализация — так и roadmap был задуман (Milestone 1 → `likec4-adapter` + `architecture-graph` + `repo-local-adapter`, и т.д.).

### Следующий шаг — Milestone 1

LikeC4 Parser/Validator + LocalRepositoryAdapter + Architecture Graph.

Начинать нужно с **technical spike**: реально установить `likec4`/`@likec4/core` и на маленьком тестовом наборе `.c4`-файлов проверить:
1. Как получить распарсенную/разрешённую модель программно (через `./model`/`./model/builder`) без записи файлов на диск — это нужно для `validateTechnical`, который по контракту должен работать на "гипотетическом слитом состоянии" (existing + generated fragments) в памяти.
2. Какой формат диагностик отдаёт парсер (Langium) и как их транслировать в `LikeC4Diagnostic`.
3. Реалистичность экспорта view в SVG без Playwright/CLI — то есть до какой степени `./react`-компонент можно рендерить headless на сервере (например, через `react-dom/server`) для `renderViewsPreview`, либо стоит ли эту функцию вообще выполнять на клиенте (в браузере, где `./react` компонент и так предназначен работать), а не на сервере.

Если результат spike'а покажет, что in-memory validate неудобен или недокументирован — это будет первый серьёзный кандидат на пересмотр архитектурного решения из плана (раздел "Валидация... на гипотетическом слитом состоянии"), и это стоит явно обсудить, а не тихо обходить костылём (запись во временную директорию на диске — рабочий, но менее чистый fallback).

## Milestone 1 — LikeC4 Parser/Validator + LocalRepositoryAdapter + Architecture Graph

### Результаты technical spike (реальный `likec4@1.59.3`)

Установил пакет в изолированную scratch-директорию и прогнал реальные вызовы на тестовых `.c4`-фикстурах (валидной и намеренно битой), прежде чем писать код адаптера. Ключевые находки:

1. **Публичный API — `LikeC4.fromWorkspace(path)`, не in-memory multi-file парсинг.** `LikeC4.fromSource(string)` существует, но принимает только один-единственный source-string (для сниппетов), не набор файлов. Никакого документированного способа скормить несколько виртуальных файлов в память без обращения к файловой системе не нашлось.
2. **`parsedModel()` / `computedModel()` дают богатый программный доступ**: `elements()`, `relationships()`, `views()` — именно то, что нужно для `ArchitectureGraph`. Работают даже на **частично невалидном** проекте — возвращают best-effort модель рядом с диагностиками, не бросают исключение. Это удобно: `parseProject` может всегда возвращать `{graph, diagnostics}` вместе.
3. **`getErrors()`/`hasErrors()`** дают message + точный range (line/character) + `sourceFsPath` — прямое сырьё для `LikeC4Diagnostic`. Но это **только ошибки**, отдельного списка warnings на уровне публичного фасада `LikeC4` нет.
4. **Точные file+line для элементов/связей/views** (`ArchitectureElement.sourceRef` и т.д.) получаются через `LikeC4ModelLocator.locateElement/locateRelation/locateView` — задокументированный, экспортируемый класс, но реально достижим только через `instance.langium.likec4.likec4.ModelLocator`, а поле `langium` в `.d.ts` помечено `protected`. TypeScript `protected` — это compile-time, не runtime, ограничение, так что путь рабочий, но это доступ к внутреннему полю в обход узкого публичного фасада `LikeC4`.
5. **Рендер SVG не требует Playwright.** `instance.viewsService.viewsAsGraphvizOut()` отдаёт готовый SVG напрямую через WASM graphviz (`@hpcc-js/wasm-graphviz`, уже зависимость `likec4`). Playwright в зависимостях CLI-пакета, судя по всему, нужен для чего-то другого (например, PNG-экспорта высокой точности или тестирования), а не для базового SVG — то, что предполагалось риском в Milestone 0, на практике не является блокером.

### Отходы от плана и почему

1. **`ArchitectureViewKind` в `core-domain` изменён** с `'system-landscape' | 'system-context' | 'container' | 'component' | 'dynamic' | 'deployment'` (C4/Structurizr-номенклатура, как её изначально описал Plan-агент) на `'element' | 'dynamic' | 'deployment'` — это реальная таксономия LikeC4 (`isElementView()` / `isDynamicView()` / `isDeploymentView()`). У LikeC4 нет встроенного деления element view на system-context/container/component — это дело соглашений конкретного проекта (Architecture Rules), а не типа view сам по себе. **Почему это важно поймать сейчас**: если бы это не проверили спайком, ошибочная модель разошлась бы по `ChangeEngine`/`Proposal`/UI кода в последующих milestones, и переделка обошлась бы намного дороже.
2. **Контракт `LikeC4Validator.validateTechnical` уточнён**: вместо буквально "in-memory, без записи на диск" — теперь "пишем гипотетическое слитое состояние во временную OS-директорию, парсим через `fromWorkspace`, удаляем директорию". Реальный проект пользователя при этом не трогается до Apply — то есть смысл требования (не портить утверждённую модель раньше времени) сохраняется, буквальная реализация — нет. Задокументировано прямо в JSDoc порта и в `temp-workspace.ts`.
3. **`likec4` запинен на точную версию `1.59.3`** (без `^`) в `packages/likec4-adapter/package.json` — намеренно, потому что `model-locator.ts` обращается к полю, помеченному `protected`, в обход узкого публичного контракта. Апгрейд версии должен быть осознанным действием (обновить версию → прогнать тесты пакета → только потом коммитить), а не тихим следствием `npm install`.
4. **Диагностики только уровня `error`.** `getErrors()` не даёт warnings на уровне публичного фасада — реализовывать доступ к warnings потребовало бы копать глубже во внутренние Langium-сервисы (тот же риск, что и с `ModelLocator`, но без документированного класса-обёртки поверх). Отложено; ФТ17 по факту требует только чтобы невалидный код не проходил в Apply — это уже обеспечено error-диагностиками.

### Что реализовано

- **`packages/likec4-adapter`**: `LikeC4NpmParser` (`LikeC4Parser`) и `LikeC4NpmValidator` (`LikeC4Validator`) поверх реального `likec4` npm-пакета; `build-architecture-graph.ts` строит `ArchitectureGraph` (elements/relationships/views + все индексы) из `parsedModel()`+`computedModel()`+`ModelLocator`; `model-locator.ts` изолирует единственное место, зависящее от internals; `temp-workspace.ts` — материализация файлов во временную директорию. 4 теста на реальном парсере (валидная модель, битый синтаксис, `validateTechnical` true/false, реальный SVG).
- **`packages/repo-local-adapter`**: `LocalRepositoryAdapter` — обход директории (`.c4`/`.likec4`, пропуская `node_modules`/`.git`), `readFile`/`readAll`, **двухфазная атомарная `writeFiles`** (сначала все файлы пишутся во временные пути рядом, и только когда все записи успешны — все `rename` разом; при сбое любого шага временные файлы подчищаются, ни один реальный файл не тронут наполовину — прямая реализация риска №6 из плана), `getRevisionInfo` через `git rev-parse` с graceful fallback для не-git папок. 6 тестов, включая happy path с реальным `git init`.

### Следующий шаг — Milestone 2

Project setup UI + Settings + SnapshotStore: экраны Create Project / Project Dashboard / Settings (Local repo), плюс `SnapshotStore` (create/restore) — переиспользующий тот же паттерн атомарной записи, что уже обкатан в `LocalRepositoryAdapter.writeFiles`. ## Milestone 2 — Project setup UI + Settings + SnapshotStore

### Технологические решения и почему именно так

**`node:sqlite` вместо `better-sqlite3`.** Проверил на месте: в Node 24 встроенный модуль `node:sqlite` (`DatabaseSync`) работает без экспериментальных флагов и без нативной пересборки. План рекомендовал "SQLite + FS" для персистентности, не называя конкретную библиотеку — выбор builtin-модуля вместо стороннего нативного аддона снижает поверхность зависимостей (важно для локального инструмента, который должен просто `npm install`-иться на любой машине пользователя без toolchain для нативных модулей) и был первым, что стоило проверить перед тем как тянуть внешний пакет. `@types/node@22.20.1` уже содержит типы для него.

**`ProjectRecord`/`ProjectStore` — минимальная модель, без полей под Confluence/Bitbucket/AI provider.** Экран Create Project по ФТ (раздел 10.2) в итоге должен спрашивать про Confluence, repository (Bitbucket или Local), AI provider/model — но эти интеграции появляются в Milestone 4 и 6. Заводить сейчас пустые опциональные поля под них означало бы проектировать модель под ещё не реализованный функционал. Добавлю их в `ProjectRecord`, когда до соответствующих milestones дойдёт очередь — это дешевле, чем поддерживать преждевременно широкий интерфейс.

**`SnapshotStore` хранит физическую копию файлов + манифест sha256 в SQLite, без content-addressable дедупликации.** В более раннем черновом дизайне (от Plan-агента, ещё на этапе планирования) упоминалась идея content-addressable store, чтобы не дублировать неизменные файлы между снапшотами. Для MVP-масштаба (единичный локальный проект, снапшоты создаются только перед Apply) это преждевременная оптимизация — простое копирование файлов проще, надёжнее и его легче тестировать на побайтовое соответствие. Если объём снапшотов на реальных проектах окажется проблемой, дедупликацию можно добавить позже, не меняя контракт `SnapshotStore`.

**Разделение "создать копию" и "применить копию".** `SnapshotStore.restore()` только возвращает `RepositoryFile[]` из сохранённой копии — запись обратно в реальный проект выполняет `RepositoryAdapter.writeFiles()` (уже с его атомарной двухфазной записью из Milestone 1). Это два independent concerns: SnapshotStore не обязан знать про конкретный repository adapter, а Apply/Rollback (Milestone 10) будет просто комбинировать оба примитива.

**Composition root получил фабрику `createLocalRepositoryAdapter(rootDir)` вместо того, чтобы роуты сами делали `new LocalRepositoryAdapter(...)`.** Прямое следствие принципа, уже зафиксированного в JSDoc `composition-root.ts` с Milestone 0 ("роуты никогда не создают адаптеры напрямую") — раньше это была декларация на будущее, теперь первый реальный кейс, где это правило применено.

### Что реализовано и как проверено

- **`packages/persistence`**: `SqliteProjectStore` (CRUD над проектами) и `FsSnapshotStore` (create/restore/list снапшотов). 9 тестов, включая прямую проверку требования из DoD плана — "восстановить snapshot и проверить побайтовое соответствие файлов" (`restore returns files byte-for-byte identical to what was snapshotted`).
- **Backend**: `POST/GET /api/projects`, `GET /api/projects/:id` — последний реально парсит LikeC4-модель через `likec4-adapter` и возвращает сводку (число элементов/связей/views + диагностику). Ни один эндпоинт не отдаёт сырую ошибку — только `UserFacingError` в теле ответа (title/likelyCause/suggestedAction), в соответствии с ФТ19.
- **Frontend**: экраны Projects (список), Create Project (форма), Project Dashboard (сводка модели + список диагностик или сообщение "модель валидна"). React Router + TanStack Query. Общий `ErrorState` компонент — единственное место в UI, рендерящее ошибки, принимает только `UserFacingError`.
- **End-to-end проверка в браузере** (не только юнит-тесты): создал реальный тестовый LikeC4-проект (`system` с двумя `service` и `database`, две связи, один view), прогнал через UI — dashboard корректно показал 4 элемента / 2 связи / 1 view и "Модель валидна, ошибок не найдено". Отдельно проверил error-state, указав несуществующую папку — сообщение понятное, без "Error 500".

### Отход от плана

Экраны Project Settings (раздел 10.4 ФТ, включая General/Confluence/Repository/AI/LikeC4/Knowledge/Architecture Rules) в явном виде из плана Milestone 2 включали только "Settings (Local repo)". Реализовал создание проекта с локальным путём прямо на экране Create Project (что уже покрывает "General" + "Repository: Local" в достаточном для DoD объёме) и отложил отдельный экран Settings как таковой — редактировать `localRepositoryPath` после создания пока негде. Это сознательно узкий скоуп: полноценный Settings UI с разделами появится, когда в проекте реально будет что настраивать помимo самого пути (Confluence — M4, AI provider — M6, Knowledge/Rules — M3) — заводить пустую страницу настроек с одним полем сейчас было бы преждевременной UI-структурой.

## Milestone 3 — Knowledge Bases & Architecture Rules

### Главное отступление от буквального DoD плана — и почему это не срыв, а честная поправка порядка milestones

DoD плана для Milestone 3 говорит: "Project KB **автоматически переиндексируется** при парсинге модели". Реализовать это буквально значило бы вызывать `EmbeddingProvider.embed()` (то есть реальный сетевой запрос к OpenAI) при каждом открытии `GET /api/projects/:id` — а Settings для ввода AI provider/API key появляются только в Milestone 6. То есть план в своём порядке milestones не учёл, что Knowledge Base зависит от готового `EmbeddingProvider`, который зависит от готового AI Settings UI.

Решение: реализовал и полностью протестировал всю инфраструктуру Knowledge Base (embedding index, global/project providers, реальный контент) как rock-solid библиотечный код через порт `EmbeddingProvider` — но **не стал** дёргать реальный `OpenAIEmbeddingProvider` из живого роута `GET /api/projects/:id`. Как только в Milestone 6 появится способ сохранить API key через UI, `ProjectKnowledgeProvider.reindexFromGraph(...)` вызывается одной строчкой сразу после `likec4Parser.parseProject(...)` в существующем роуте — переделывать ничего не придётся, контракт уже готов и покрыт тестами. Это тот же паттерн, что уже был в Milestone 1→2 (адаптеры сначала как протестированная библиотека, потом подключение к живому UI, когда для него появляется естественный повод) — здесь просто более явный пример того, почему это правило работает.

Architecture Rules CRUD, наоборот, **не имеет** такой зависимости (не нужны эмбеддинги вообще) — поэтому эта часть Milestone 3 полностью живая и проверена в браузере, как в предыдущих milestones.

### Технологические решения

**`node:sqlite` брутфорс cosine similarity вместо внешней vector DB.** Прямая реализация рекомендации плана. При объёме "один проект + одна общая KB" (десятки-сотни chunks) полный перебор в JS на каждый search быстрее по факту, чем сетевой round-trip к внешней vector DB, и не требует поднимать/настраивать ещё один сервис для локального однопользовательского инструмента.

**Контент LikeC4 Knowledge Base — файлы в `content/` + `manifest.json`, не хардкод в TS.** Прямое следствие ФТ3 ("должна обновляться независимо от версии приложения"): контент физически отделён от кода пакета, у него своя версия в manifest. Написал 6 реальных чанков (обзор синтаксиса, specification, model/relationships через `extend`, views/dynamic views, metadata/tags, best practices по расширению модели без дублей) — не исчерпывающая база, а стартовый набор, который предполагается пополнять со временем, как и задумано ФТ3.

**`KnowledgeChunk` в core-domain дополнен полем `tags: string[]`.** В исходном плане `KnowledgeQuery.tags` подразумевал фильтрацию, но у `KnowledgeChunk` не было явного поля для этого (только generic `metadata`). Вынес `tags` в отдельное поле first-class — не пряча механизм фильтрации внутри неструктурированного `metadata`.

**`SqliteEmbeddingIndex`: `replaceAll` (полная перезапись) vs `upsert` (точечно) vs `replaceByIdPrefixes` (гибрид).** Изначально написал только `replaceAll` — и почти протащил в `ProjectKnowledgeProvider` баг: полная перезапись индекса при каждой переиндексации графа стёрла бы вручную добавленные пользователем заметки (`upsert`), которых нет в самом графе. Поймал это при проектировании `reindexFromGraph`, до написания тестов, а не после бага в проде. Исправление — `replaceByIdPrefixes(['element:', 'rule:'], chunks)`: удаляет только устаревшие авто-производные chunks (по префиксу id), не трогая записи с другими id. Покрыто тестом `replaceByIdPrefixes drops stale auto-derived chunks but preserves manually added ones`.

### Обнаруженный и исправленный баг: коллизия `id` между чанками разных проектов

Первая версия схемы `knowledge_chunks` объявляла `id TEXT PRIMARY KEY` — то есть id должен был быть уникален **глобально по всей таблице**, а не в пределах одного `scopeKey`. Поскольку id чанков строятся детерминированно из доменных данных (`element:${elementId}`, `rule:${ruleId}`), два разных проекта с элементом `orderService` неизбежно дали бы одинаковый id `element:orderService` — и `upsert`/`ON CONFLICT` тихо перезаписал бы chunk одного проекта данными другого, ломая изоляцию между проектами. Поймал это до того, как написал первый тест на multi-project сценарий (не через баг-репорт, а просто задав себе вопрос "а что если у двух проектов одинаковый id элемента?"), исправил на составной `PRIMARY KEY (scope_key, id)` и сразу закрепил регрессионным тестом (`the same chunk id in two different scopes does not collide`).

### Найденный и исправленный баг в уже существующем (Milestone 2) UI при живой проверке

При проверке Architecture Rules CRUD в браузере кнопка "Удалить" не работала — DELETE-запрос падал с `400 FST_ERR_CTP_EMPTY_JSON_BODY`. Причина жила в `apps/web/src/api/client.ts` ещё с Milestone 2: общий `request()` хелпер всегда добавлял заголовок `Content-Type: application/json`, даже когда тела запроса нет (DELETE) — Fastify по умолчанию отвергает пустое тело с этим заголовком. Юнит-тесты этого не поймали бы (они не гоняют реальный HTTP через настоящий Fastify) — только визуальная проверка в браузере, которую делаю по требованию для любых фронтенд-изменений. Исправлено: `Content-Type` теперь ставится только когда есть `init.body`. Это подтверждает практическую пользу правила "всегда проверять UI в браузере, а не только типами/юнит-тестами" — этот конкретный баг был бы незаметен до первого реального клика пользователя.

### Что реализовано и как проверено

- **`packages/persistence`**: `SqliteArchitectureRuleStore` (CRUD, скоуп по projectId), `SqliteEmbeddingIndex` (`replaceAll`/`upsert`/`replaceByIdPrefixes`/`search` с cosine similarity и tag-фильтром). +11 тестов (20 итого в пакете).
- **`packages/llm-openai`**: `OpenAIEmbeddingProvider` — реальный HTTP-клиент к OpenAI Embeddings API, `fetchImpl` инжектируется для тестов без сети/ключа. Тесты проверяют, что ключ уходит только в заголовок запроса и никогда не попадает в текст ошибки.
- **`packages/knowledge-global`**: `GlobalKnowledgeProvider` + 6 реальных markdown-чанков про синтаксис LikeC4. Ленивая индексация (не пересчитывает эмбеддинги на каждый старт, пока контент не пуст). Тесты используют детерминированный fake-embedding-provider (bag-of-words хеширование) — реальный поиск по реальному контенту, без сети.
- **`packages/knowledge-project`**: `ProjectKnowledgeProvider.reindexFromGraph(graph, rules)` — индексирует элементы графа и Architecture Rules; тест напрямую проверяет DoD-требование "rules фильтруются по kind в поиске" через `tags`.
- **Architecture Rules — полностью живая часть**: backend (`GET/POST/PATCH/DELETE /api/projects/:id/architecture-rules`) + экран `/projects/:id/architecture-rules` (список, форма создания/редактирования, удаление). Проверено в браузере: создание правила → редактирование severity → удаление, все три шага подтверждены реальными скриншотами.

## Milestone 4 — Confluence Adapter + Bitbucket Adapter (read-only)

### Остаточный риск: не проверено на реальном сервере

Спросил пользователя про доступ к тестовому Confluence Server/DC заранее (как и планировал в конце Milestone 3) — пользователь предпочёл не давать доступ сейчас и попросил поступить с Confluence так же, как решили с Bitbucket: реализовать по документированному API и проверить моками HTTP, без живого сервера. Это осознанно принятый пользователем trade-off, а не моё решение срезать угол — фиксирую явно: **разбор storage-format проверен только на синтетических примерах**, пусть и максимально точных по структуре (heading/paragraph/list/table/code-macro/layout-контейнеры/image caption, основано на документированном формате Confluence storage). Риск №4 из плана остаётся открытым до первой реальной проверки — рекомендую сделать её при первой возможности, до того как на этот адаптер начнёт полагаться AI pipeline (Milestone 5+).

### Технологические решения

**`htmlparser2` + `domhandler` для разбора storage-format, вместо regex.** Confluence storage format — XHTML-подобный XML с псевдо-namespace тегами (`ac:structured-macro`, `ri:attachment`). Пробовал бы решить только регулярками — почти гарантированно сломался бы на вложенных структурах (таблица внутри layout-cell внутри macro rich-text-body). `htmlparser2` с `xmlMode: true` сохраняет `ac:`-теги и атрибуты как обычные строковые имена (проверил на месте перед тем как писать код) — то есть не пытается их резолвить как настоящие XML namespace, что и нужно для этого формата без специальной обработки. Не стал добавлять отдельный пакет `domutils` — использую `DomUtils`, который `htmlparser2` уже ре-экспортирует сам.

**Разбор через рекурсивный обход с allowlist известных блоков**, а не через плоский перебор верхнего уровня. Confluence оборачивает контент в `ac:layout`/`ac:layout-section`/`ac:layout-cell` при использовании page layouts — плоский обход пропустил бы весь такой контент. Вместо allowlist контейнерных тегов алгоритм рекурсивно обходит *любой* незнакомый тег в поисках знакомого контента (paragraph/list/table/macro/image), что устойчиво к любой глубине вложенности без необходимости перечислять все возможные контейнеры Confluence.

**Bitbucket Server: конфигурируемая `likec4Directory`, пути в `RepositoryFile` — относительно неё, не относительно корня репозитория.** Прямая реализация ФТ5 ("указать directory LikeC4"). Листинг файлов идёт через единственный endpoint `/files` (отдаёт вообще все пути в репозитории за постранично, без server-side фильтрации по директории) — фильтрация по `likec4Directory`-префиксу и расширению происходит на нашей стороне после получения полного списка. Для MVP-масштаба репозиториев это нормально; для очень больших монорепов это стоило бы пересмотреть позже (не сейчас — YAGNI).

**PAT обоих Server/DC-адаптеров — одна и та же схема (`Authorization: Bearer <token>`).** Confluence Server/DC (7.9+) и Bitbucket Server/DC используют идентичную PAT-авторизацию через Bearer-токен — оба адаптера получили одинаковый паттерн `#authHeaders()`, что не случайное совпадение, а следствие того, что оба продукта — часть одной платформы Atlassian Server-продуктов.

### Обнаруженный и исправленный баг: "дыра" в headingPath, если страница не начинается с h1

Первая версия `walk()` записывала заголовок по индексу `headingPath[level - 1]`, усекая массив до `level - 1` элементов. Работает, если заголовки идут по порядку от h1 — но реальные Confluence-страницы нередко начинают сразу с h2 (h1 иногда вообще не используется как разметочный уровень, а служит только для крупного заголовка страницы, отдельного от структуры body). В этом случае `headingPath[1] = "..."` при пустом `headingPath[0]` оставляет `undefined` на месте пропущенного уровня — сломанный `headingPath: [undefined, "Заголовок"]` вместо `["Заголовок"]`. Поймал это не через рассуждение "а что если...", а через свой же тест на layout-контейнер с `<h2>` внутри без предшествующего `<h1>` — тест сразу упал. Переписал на стек `{level, text}[]`, который просто схлопывает всё glubже-или-равно текущему уровню перед push — не зависит от того, с какого уровня страница начинается. Закреплено отдельным регрессионным тестом с явным названием.

### Что реализовано и как проверено

- **`packages/confluence-adapter`**: `parseStorageFormat()` (17 тестов: heading nesting, list/table/code-macro extraction, macro degradation, layout-recursion, image caption, стабильность id) + `ConfluenceServerAdapter` (PAT только в заголовке, корректный URL/expand-параметры, обработка 401/403/сетевых ошибок).
- **`packages/repo-bitbucket-adapter`**: `BitbucketServerAdapter` — пагинация `/files`, фильтрация по `likec4Directory`+расширению, `raw`-чтение файлов, `getRevisionInfo` через `/commits`, `writeFiles` явно бросает ошибку read-only. 8 тестов.
- Оба адаптера **не подключены** к `composition-root`/UI в этом milestone — сознательно отложено, см. ниже.

### Отход от плана: Settings UI для Confluence/Repository отложен

План описывал Milestone 4 как включающий "Settings UI разделы Confluence/Repository(Bitbucket toggle)". Не стал делать это в этом же заходе: подключение потребовало бы содержательного изменения модели `ProjectRecord` (сейчас `localRepositoryPath: string`, нужно стало бы `repository: RepositoryConfig` — union local/bitbucket) и новых полей для Confluence-настроек (`baseUrl` + PAT в SecretsVault), затрагивая уже написанные в Milestone 2 роуты и экраны. Это осмысленный, но отдельный по объёму рефакторинг, который не хотелось смешивать с уже большим объёмом работы над самими адаптерами в одном заходе. Оба адаптера полностью реализованы и покрыты тестами как самостоятельные, готовые к подключению модули (тот же паттерн "библиотека сначала, проводка в UI — когда до неё естественно доходит очередь", что и раньше). Следующий логичный шаг — либо это подключение, либо переход к Milestone 5 (Pipeline Orchestrator), в зависимости от того, что нужнее пользователю раньше.

## Milestone 5 — Pipeline Orchestrator skeleton + стадии 1-5

### Пришлось сначала доделать отложенное из Milestone 4 — и это было правильным решением

Пользователь выбрал продолжать сразу с Milestone 5, но стадия 1 pipeline (Load Confluence) физически невозможна без настроенного подключения к Confluence на уровне проекта — а это ровно то, что было сознательно отложено в конце M4. В этот раз выбор был не "либо/либо", а необходимость: пришлось добавить `confluenceBaseUrl` в `ProjectRecord` и полноценный Settings-экран для Confluence (baseUrl + PAT через `SecretsVault`, с реальной проверкой подключения). Полный рефакторинг `ProjectRecord` под `RepositoryConfig`-union (local/bitbucket) при этом НЕ делал — Bitbucket по-прежнему не подключён к UI, потому что pipeline стадии 3 (Load LikeC4) для локального репозитория достаточно, чтобы доказать всю цепочку целиком; расширение на Bitbucket остаётся отдельной, не блокирующей задачей.

### Ключевое архитектурное решение: `run()` без отдельного `resume()`

Дизайн из плана предполагал отдельный метод возобновления сессии. Спроектировал иначе: `PipelineStageDef.isDone(stageOutputs)` определяет, выполнена ли стадия, по факту наличия её результата в `stageOutputs` — не по номеру шага и не по значению `currentStage`. Благодаря этому `run()` идемпотентен по конструкции: "запустить с нуля" и "продолжить после падения процесса" — один и тот же вызов с одной и той же сигнатурой, разница только в том, пустые ли `stageOutputs` у переданной сессии. Отдельного `resume()`/`startFromIndex` не потребовалось вовсе. Это не просто короче — это меньше состояния, которое может рассинхронизироваться между `currentStage` и тем, что реально посчитано.

Прямое следствие этого решения — комбинирование плановых стадий 4 (Parse LikeC4) и 5 (Build Architecture Graph) в один `PipelineStageDef` с id `build-architecture-graph`. `LikeC4Parser.parseProject()` (Milestone 1) считает parse и построение графа атомарно за один вызов библиотеки — между ними нет наблюдаемого промежуточного состояния. Если завести для них два отдельных `PipelineStageDef` с общим условием `isDone` (оба проверяли бы наличие `architectureGraph`), вторая стадия автоматически оказывалась бы "уже выполненной" сразу после первой и никогда бы не получала свой собственный статус/checkpoint — `isDone`-модель просто не может корректно выразить две стадии с одним результатом. Не костыль, а прямое следствие атомарности используемой библиотеки; задокументировано в коде стадии.

### Обнаруженный и исправленный баг — снова через собственную же проверку в браузере

При первой живой проверке (реальный SSE через браузер, не мок) сообщение об ошибке провалившейся стадии выглядело так: `Не удалось выполнить шаг "Reading Confluence"` — русское предложение с английским названием стадии внутри. Причина: `PipelineStageDef.label` изначально был на английском (как в примере из текста плана), а `userFacingTimeline`/сообщения об ошибках — тоже на английском по построению `advance()`/`fail()`, но сам текст вокруг — русский. Юнит-тесты этого не поймали бы (они проверяют `stage` id, не текст label). Поймал глазами на реальном скриншоте при целенаправленной проверке error-state (специально останавливал фейковый Confluence-сервер, чтобы увидеть failed-состояние). Перевёл все 4 label на русский.

### Технологическое решение: fake Confluence Server вместо мока в браузерной проверке

Для visual-проверки в браузере (обязательной для фронтенд-изменений) поднял отдельный локальный Node HTTP-сервер, имитирующий Confluence Server REST API (`/rest/api/space`, `/rest/api/content/:id`) с реалистичным storage-format телом (heading/paragraph/table/code-macro). Это не то же самое, что реальный Confluence Server (не проверяет реальные особенности конкретной инсталляции — тот риск из Milestone 4 остаётся открытым), но даёт нечто существенно более сильное, чем мокнутый `fetch` в юнит-тестах: настоящий HTTP round-trip через реальный `ConfluenceServerAdapter`, реальный Fastify SSE-эндпоинт и реальный EventSource в браузере. Именно так был пойман баг с английским label выше — через юнит-тесты (мокнутый fetch) он был бы не виден, потому что тесты проверяют структуру данных, а не то, как ошибка реально выглядит в интерфейсе.

### Что реализовано и как проверено

- **`packages/core-pipeline`**: `PipelineOrchestrator` + 4 стадии (`load-confluence`, `parse-specification`, `load-likec4`, `build-architecture-graph`, последняя покрывает и плановую стадию "parse-likec4"). 4 теста: полный прогон, возобновление после симулированного рестарта процесса (перечитывание сессии из реального `SqliteSessionHistoryStore`, не in-memory объекта), сохранение состояния `failed` с прогрессом до сбоя, повторный запуск упавшей сессии с успешным результатом.

- **Frontend**: `ConfluenceSettingsPage`, `NewTaskPage`, `AnalysisPage` (живой чеклист 4 стадий через `EventSource`, сводка по завершении, understandable error-state при сбое).
- **End-to-end проверка в реальном браузере** (не только юнит-тесты): полный happy path через fake Confluence Server — создание проекта → настройка Confluence → запуск задачи → все 4 стадии дошли до ✓ → "Готово: Refund Flow Spec" с правильными счётчиками (3 чанка спецификации, 1 файл модели, 4 элемента, 1 view, что в точности соответствует тестовым данным). Отдельно проверен error-state (остановленный Confluence-сервер) — понятное сообщение, без утечки английского текста после перевода label'ов.

## Milestone 6 — LLMProvider (OpenAI) + ContextBuilder + стадии 6-8

### `completeJSON` через `response_format: json_object`, а не строгий `json_schema`

OpenAI поддерживает два режима структурированного вывода: мягкий `{type: 'json_object'}` (гарантирует валидный JSON, но не гарантирует конкретную форму) и строгий `json_schema` (гарантирует форму по схеме, но требует более капризного и многословного описания схемы, плюс не все модели/версии API одинаково хорошо его поддерживают). Выбрал первый вариант: код сам валидирует форму ответа после парсинга (проверка `chunkId`/`category` на этапе Extract Requirements, проверка `matchedElementId` на этапе Entity Matching — см. ниже про hallucination guard) — то есть валидация всё равно нужна на стороне приложения, а не только на стороне OpenAI, значит выгода от строгой схемы меньше, чем цена усложнения промпта. Простое решение, которого достаточно.

### Три уровня защиты от неверного entity-matching — это осознанный, а не избыточный дизайн

Сопоставление извлечённого требования с существующим элементом архитектуры — самое рискованное место всего pipeline (ошибка здесь тихо тиражируется дальше, во все последующие стадии). Поэтому `LLMChangeEngine.matchEntities()` — это не один вызов LLM, а конвейер из трёх независимых защит:

1. **Лексический предфильтр** (`lexicalCandidates`) — если у требования нет вообще ни одного общего слова ни с одним элементом графа, LLM не вызывается совсем: результат сразу `{confidence: 0, ...}`. Экономит вызовы и, что важнее, устраняет источник голых "давай угадаем" ответов модели на пустом месте.
2. **LLM-судья получает не голые id, а полные карточки кандидатов** (id, kind, title, description) — иначе у модели физически нет данных, чтобы вынести смысловое суждение (см. баг ниже).
3. **Hallucination guard** — после ответа LLM код проверяет, что `matchedElementId` действительно входит в список предложенных кандидатов; если модель "придумала" id, которого не было в списке — принудительно `confidence: 0` с объяснением в `rationale`, а не доверие галлюцинации.

Ни один из трёх уровней не заменяет остальные: предфильтр не понимает смысл, судья может ошибиться или сгаллюцинировать, guard ловит только один конкретный класс ошибок (несуществующий id), но не "неверный, но существующий" id — эту последнюю категорию ошибок сознательно оставляем на откуп порогу уверенности (`AUTO_CONFIDENT_THRESHOLD = 0.75` в Gap Analysis, ниже которого выставляется `needsClarification` и решение уходит человеку, а не применяется автоматически).

### Найденный и исправленный баг №1: буст по kind позволял кандидату пройти фильтр без единого общего слова

Первая версия `lexicalCandidates` считала `score = overlap + kindBoost` и фильтровала по `score > 0` — то есть элемент "вероятного" kind (например, `service` для категории `new-service`) проходил фильтр даже при нулевом текстовом пересечении с требованием, просто за счёт буста `+0.2`. Это ломало ровно то поведение, ради которого предфильтр существует ("нет пересечения → не вызывать LLM"): требование без единого общего слова с графом внезапно получало кандидатов. Поймано golden-тестом "требование без лексического пересечения не должно вызывать LLM" — тест упал с `ScriptedLLMProvider: ran out of scripted responses`, что и доказало лишний вызов. Исправлено: `overlap > 0` — обязательный фильтр, kind-буст применяется только как тай-брейкер ранжирования уже прошедших фильтр кандидатов.

### Найденный и исправленный баг №2: судье передавались голые id вместо описаний кандидатов

`#judge()` изначально формировал промпт как `Кандидаты (id): ${candidateIds.join(', ')}` — то есть LLM должна была выносить семантическое суждение о совпадении, имея на руках только id без title/kind/description. Для реального смыслового сравнения ("это то же самое, о чём говорит требование, просто другими словами?") это категорически недостаточно. Исправлено на полные карточки кандидатов; добавлен отдельный регрессионный тест, что промпт содержит "Order Service", "kind: service" и текст описания, а не только id.

### Найденный и исправленный баг №3 (при живой проверке в браузере): английская подпись кнопки на русскоязычном экране

Тот же класс бага, что уже дважды ловился в Milestone 5 (английский `label` стадии в русском сообщении об ошибке): при browser E2E для Milestone 6 кнопка запуска анализа на `NewTaskPage` (унаследованный экран ещё из Milestone 5, не тронутый в M6) показывала `Analyze Specification` вместо перевода. Юнит-тесты не могли это поймать — они не рендерят JSX и не проверяют текст кнопок. Исправлено на "Проанализировать спецификацию", подтверждено через HMR прямо во время той же browser-сессии без перезапуска dev-сервера. Практический вывод тот же, что и в M5: обязательная браузерная проверка регулярно ловит именно этот класс бага, который не виден никаким другим типом теста в этом проекте.

### Осознанное решение по объёму: `ContextBuilder` написан, но не подключён к стадиям 6-8

`ContextBuilder` (BFS-срез графа по seed-элементам + trim по токен-бюджету + подмешивание knowledge-чанков) реализован и покрыт тестами, но стадии 6-8 его не используют — `#judge()` в entity-matching обходится точечным обогащением промпта карточками кандидатов, этого достаточно для задачи "сравнить одно требование с 1-5 кандидатами". Полноценный срез графа с депth-BFS нужен там, где решение принимается по контексту всей подсистемы, а не по паре сущностей — это Proposal Generation / LikeC4 Generation (Milestone 8/9), где реальный первый потребитель `ContextBuilder` появится. Собрать компонент заранее, но подключить только когда он реально нужен — то же самое рассуждение, что было с `KnowledgeProvider` между Milestone 3 и Milestone 6 (протестированная, но не подключённая библиотека, пока не появился настоящий потребитель).

### Что реализовано и как проверено

- **`packages/llm-openai`**: `OpenAILLMProvider` (`complete`/`completeJSON`/`estimateTokens`) + `testOpenAIConnection`, инжектируемый `fetchImpl`, ключ никогда не логируется и не попадает в текст ошибки (проверено отдельными тестами на malformed-JSON и HTTP-error путях).
- **`packages/context-builder`** (новый пакет): `sliceGraph` (BFS + цепочка родителей) + `ContextBuilder.build()` (срез → trim по бюджету → фильтр применимых правил → knowledge-чанки).
- **`packages/change-engine`** (новый пакет, ключевая часть milestone): `LLMChangeEngine` — `matchEntities`/`detectGaps`/`resolveConflicts`, `mapCategoryToProposalType` (ФТ7 "не дублировать": даунгрейд `new-*` → `modified-*` при найденном совпадении), `lexicalCandidates`. 10 golden-тестов на `ScriptedLLMProvider`.
- **`packages/core-pipeline`**: стадии `extract-requirements`, `entity-matching`, `gap-analysis` (стадии 6-8), `OrchestratorPorts` расширен опциональными `llmProvider`/`changeEngine`/`architectureRuleStore`/`knowledgeProviders` (опциональность сохраняет обратную совместимость фикстур M1-M5 без AI-настроек).

- **Frontend**: `AISettingsPage` (зеркало `ConfluenceSettingsPage`), `AnalysisPage` — 3 новых пункта чеклиста стадий + вторая строка статистики (требований извлечено / сопоставлено / предложений изменений).
- **End-to-end проверка в реальном браузере**: создание проекта → Confluence settings (fake Confluence Server на :4501) → AI settings (fake OpenAI-совместимый сервер на :4502, честная проверка через `GET /v1/models`) → запуск задачи → все 7 стадий дошли до ✓ через живой SSE → "Готово: Refund Flow Spec" с корректными счётчиками (3 чанка, 1 файл модели, 4 элемента, 1 view, 2 требования извлечено, 2 предложения изменений). Именно на этом прогоне найден и исправлен баг №3 выше.

### Остаточный риск, зафиксированный намеренно

Как и Confluence/Bitbucket в Milestone 4/5, этот milestone проверен только против **фейкового** OpenAI-совместимого сервера — реальный `api.openai.com` не вызывался ни разу (пользователь не поделился реальным ключом, что было ожидаемо и учтено заранее). Фейковый сервер в этой проверке нарочно упрощён: judge-вызов для entity-matching **не** оценивает семантику кандидата, а просто возвращает `confidence: 0.88` для первого id, встретившегося в промпте, — это объясняет, почему при 2 извлечённых требованиях ("новый Refund Service" и "доработка Order Service") итоговое `matchedRequirementCount` в проверке получилось 2, а не 1: слово "order" случайно встретилось в тексте требования про Refund Service ("independent of order processing"), из-за чего лексический предфильтр законно предложил `orderService` кандидатом и для него тоже — а настоящая модель, в отличие от фейковой, скорее всего отклонила бы этот кандидат по смыслу. Это ограничение тестового стенда, а не баг production-кода (три уровня защиты выше рассчитаны именно на то, что реальная модель способна отличить "совпадение по слову" от "совпадение по смыслу"); зафиксировано здесь, а не исправлено, потому что исправлять фейковый сервер до полноты реальной модели бессмысленно — единственная настоящая проверка этого риска возможна только с реальным OpenAI API.

### Следующий шаг — Milestone 7

## Внеплановый проход — подключение любого open-source / OpenAI-совместимого LLM

Пользователь спросил, что нужно сделать, чтобы подключать к проекту любую open-source LLM-модель, а не только OpenAI. Не относится ни к одному конкретному пункту плана — фиксирую здесь отдельным разделом, как и репозиторную гигиену ранее.

### Ключевое наблюдение, определившее весь подход

Почти все open-source серверы для локальных моделей — Ollama, vLLM, LM Studio, llama.cpp server — уже реализуют протокол OpenAI Chat Completions (`/v1/chat/completions`, `/v1/models`, часто и `/v1/embeddings`). `OpenAILLMProvider`/`OpenAIEmbeddingProvider` (Milestone 6) уже физически говорят на этом протоколе и уже умели принимать произвольный `baseUrl` — просто это было доступно только как server-wide env-переменная для тестового стенда, а не как настройка проекта, и `apiKey` был жёстко обязателен и в форме, и в backend, и в самом HTTP-запросе. Поэтому решение — не писать новый адаптер под каждый локальный сервер, а снять именно эти три ограничения в уже существующем.

Пользователь явно подтвердил (через уточняющий вопрос перед реализацией): класс/пакет `OpenAILLMProvider`/`@likec4-ai/llm-openai` **не переименовываем** — они уже названы по протоколу, а не по вендору, что и так корректно; и расширяем **сразу оба** — LLM и эмбеддинги — по одному и тому же принципу.

### `apiKey` стал необязательным на всех трёх уровнях

Раньше: форма требовала apiKey всегда, backend-роут `ai-settings.ts` отвечал 400 при пустом apiKey, а сам HTTP-запрос буквально подставил бы `Bearer undefined`, если бы это как-то обошли. Убрал все три — заголовок `Authorization` теперь просто не добавляется, если ключа нет (`OpenAILLMProvider`/`OpenAIEmbeddingProvider`/`testOpenAIConnection`). Backend больше не валидирует apiKey вручную — вместо этого `testOpenAIConnection` сам честно вернёт 401-ошибку, если ключ реально был нужен (настоящему OpenAI), а для локального сервера, которому ключ не нужен, тест просто пройдёт. Одна проверка вместо двух дублирующих друг друга.

### `baseUrl` стал настройкой проекта, а не только тестовым env-хаком

Добавлено поле `aiBaseUrl` в `ProjectRecord` (по образцу `confluenceBaseUrl`) + колонка в SQLite + поле в AI Settings UI. Приоритет при выборе адреса: настройка проекта → server-wide env `LIKEC4_AI_OPENAI_BASE_URL` (остаётся как deployment-wide дефолт, например если вся организация стандартизировалась на одном self-hosted сервере) → дефолт `api.openai.com` внутри самого провайдера.

### Побочный, но необходимый эффект: переопределено значение `configured`

Пока apiKey был обязателен, `configured` в GET `/ai-settings` означал "есть сохранённый ключ в SecretsVault". С keyless-провайдерами это стало неверным — локальный сервер без ключа вечно показывал бы "ещё не настроено", хотя реально работает. Заменил на `project.aiModel !== undefined` — это поле пишется только после успешного прохождения `testOpenAIConnection`, то есть корректно отражает "хотя бы раз подтверждённое подключение" независимо от того, нужен ключ или нет. Тот же сдвиг сделан в гейте запуска задачи в `sessions.ts` (было: "нет ключа → отказ", стало: "не настроено ни разу → отказ").

### `completeJSON` научился переживать один невалидный JSON-ответ

Не все локальные модели одинаково хорошо соблюдают `response_format: json_object` — некоторые бэкенды просто игнорируют этот параметр. Раньше первый же невалидный JSON сразу ронял `completeJSON` (а с ним — всю стадию pipeline). Теперь при ошибке парсинга код повторяет запрос один раз, добавив явное текстовое напоминание ("ответь строго валидным JSON без markdown"), и только если не помогло — бросает ошибку. Дороже по латентности только на пути отказа, но заметно устойчивее к слабой поддержке structured output части локальных моделей.

### Что реализовано и как проверено

- **`packages/llm-openai`**: `apiKey?` необязателен у `OpenAILLMProvider`/`OpenAIEmbeddingProvider`/`testOpenAIConnection`; `isLocal` теперь вычисляется (`baseUrl !== 'https://api.openai.com/v1'`), а не хардкодится; retry-фоллбэк для `completeJSON`. 6 новых тестов (keyless-запрос без Authorization header — LLM/embeddings/connection; retry-успех; retry-неудача дважды; `isLocal` true/false).
- **`packages/core-domain`**: `ProjectRecord.aiBaseUrl?: string`.
- **`packages/persistence`**: колонка `ai_base_url`, чтение/запись, новый regression-тест.
- **`apps/server`**: `composition-root.ts` прокидывает `baseUrl`/необязательный `apiKey` в обе фабрики; `ai-settings.ts` — `baseUrl` в теле запроса, apiKey можно не указывать повторно при обновлении (подставляется уже сохранённый), `configured`/гейт запуска задачи больше не завязаны на наличие ключа.
- **Frontend**: `AISettingsPage` — новое поле "Адрес сервера", API key больше не `required`, текст явно упоминает Ollama/LM Studio/vLLM/llama.cpp server.
- **Живая браузерная проверка** (обязательна для фронтенд-изменений) — два отдельных прогона:
  1. Полностью keyless сценарий: новый проект → AI Settings с пустым API key и `baseUrl` на третий фейковый сервер (:4503, намеренно игнорирующий Authorization и логирующий предупреждение, если бы его всё-таки прислали) → "Подключение настроено" без единого введённого символа в поле ключа → запуск задачи → все 7 стадий дошли до ✓. В логе фейкового сервера подтверждено отсутствие заголовка Authorization на всех вызовах, включая все 3 обращения к `/v1/chat/completions`.
  2. Регрессия старого пути: второй проект, apiKey заполнен, `baseUrl` пуст (значит используется fallback на env-переменную, как в Milestone 6) → тоже "Подключение настроено", тоже все 7 стадий до конца.

### Осознанно не сделано в этом заходе

- Не переименован пакет/классы (решение пользователя, см. выше).
- Не добавлена отдельная настройка `baseUrl`/ключа под эмбеддинги отдельно от чата — один и тот же `aiBaseUrl` и один и тот же секрет используются для обоих, поскольку `createEmbeddingProvider` пока нигде не вызывается вживую (см. Milestone 6 про отложенное подключение `KnowledgeProvider`) — заводить вторую настройку без второго живого потребителя было бы преждевременной абстракцией.
- Замечена, но не тронута отдельная нестыковка в `confluence-settings.ts`: там PAT-поле на фронтенде подписано "оставьте пустым, чтобы не менять", но backend всё равно требует непустой `token` на каждый POST — то есть на практике так нельзя обновить только `baseUrl` Confluence, не введя PAT заново. Это не связано с open-source LLM и существовало ещё с Milestone 5 — сообщаю пользователю отдельно, чинить не стал, чтобы не расширять эту задачу за её границы.

## Milestone 7 — Ambiguity Detection + Questions UI (стадии 9-10)

### Самокоррекция: в предыдущей записи была неверно указана следующая веха

В конце раздела Milestone 6 выше написано "Следующий шаг — Milestone 7: по плану — Proposal Generation (стадия 9)". Это ошибка: по `docs/development-plan.md` (раздел Roadmap) Milestone 7 — это **Ambiguity Detection + Questions UI (стадии 9-10)**, а Proposal Generation — стадии 11-12, Milestone 8. Ошибка обнаружена и исправлена перед началом работы, при сверке с самим документом плана, а не оставлена как есть — фиксирую как пример того же принципа, что и самокоррекция про `.gitignore` при репозиторной гигиене: собственные более ранние записи стоит перепроверять по первоисточнику, а не считать авторитетными по умолчанию.

### Хорошая новость: модели данных для этого были готовы с Milestone 0

`ClarificationQuestion`, `QuestionOriginKind`, `QuestionStatus`, `PipelineState.pendingQuestionIds`, `SessionRecord.questions`, `ConflictNote`, `ArchitectureChangeCandidate.needsClarification` — все уже существовали как типы, спроектированные ещё на старте проекта, и `LLMChangeEngine.resolveConflicts()` (Milestone 6) уже был реализован и покрыт тестами, просто не вызывался ни одной стадией pipeline. Сами комментарии в коде M6 (`gap-analysis.ts`, `llm-change-engine.ts`) явно указывали: "стадия 9, Milestone 7, решает, что делать дальше" — этот milestone в основном подключил уже готовые провода, а не проектировал домен с нуля.

### Ключевое архитектурное решение: гейт-стадии как расширение уже существующей idiom `isDone`

Стадия 10 (User Clarification) не вычисляет ничего — она ждёт внешнего события (ответ пользователя). Вместо отдельного механизма "пауза pipeline" завёл на `PipelineStageDef` необязательное поле `isGate?: boolean` (`packages/core-pipeline/src/stage.ts`): пока `isDone()` гейта возвращает false, `PipelineOrchestrator.run()` не вызывает `run()` этой стадии вовсе, а останавливается с `status: 'paused-for-user'` и возвращает управление немедленно — то же самое "не ошибка, а осознанная точка паузы", что и `paused-for-user` в `PipelineStatus`, спроектированном ещё в Milestone 0.

`isDone` гейта — `outputs.ambiguities.every(q => q.status !== 'open')` — то есть просто читает уже посчитанный `stageOutputs.ambiguities` (Milestone 9), а не отдельное собственное состояние. Это то же самое рассуждение, что и с комбинированием стадий 4+5 в Milestone 5: не заводить дублирующее состояние, когда решение уже выражается через существующее поле.

Прямое следствие этого дизайна — `PipelineOrchestrator.run()` пришлось научить закрывать сессию статусом `'completed'` даже когда последняя стадия STAGES была пропущена через `continue` (уже done ещё ДО входа в цикл), а не только когда она только что реально выполнилась через `advance()`. Раньше это было не нужно — до Milestone 7 ни одна стадия не могла стать "done между двумя вызовами `run()`" без того, чтобы сама её выполнить. Добавлена проверка после цикла: если статус ещё не `'completed'` — выставить явно. Без неё сессия, чей единственный открытый вопрос только что ответили, зависла бы в `'paused-for-user'` навсегда, хотя весь pipeline уже пройден.

### `pendingQuestionIds` — вычисляемая проекция, а не отдельно поддерживаемое состояние

Модель поля (`PipelineState.pendingQuestionIds: string[]`) существовала с Milestone 0 как список "что ещё не отвечено". Вместо того чтобы мутировать этот список отдельно от `stageOutputs.ambiguities` в нескольких местах (стадия 9, гейт-пауза, роут ответа на вопрос) — что рано или поздно разошлось бы, как предупреждает объяснение design'а `isDone` из Milestone 5 — вынесена одна чистая функция `computePendingQuestionIds(ambiguities)` (`packages/core-pipeline/src/pending-questions.ts`), вызываемая из обоих мест, где список может измениться (пауза оркестратора и `POST /questions/:id/answer`). Единственный источник истины — сам список вопросов; `pendingQuestionIds` — просто его открытая проекция, пересчитываемая, а не хранимая независимо.

### Три уровня защиты, аналогичные Milestone 6, применены и здесь

Стадия 9 (Ambiguity Detection) не изобретает новую логику принятия решений — она берёт уже посчитанные сигналы двух предыдущих стадий (`needsClarification` из Gap Analysis, `remainingConflict` из `resolveConflicts`) и переводит их в явные вопросы вместо тихого выбора. Намеренно НЕ добавлено содержательное (семантическое) разрешение конфликтов через отдельный LLM-вызов — `resolveConflicts` по-прежнему распознаёт только структурный случай "несколько требований целятся в один и тот же существующий элемент", как и было в Milestone 6. DoD этого milestone по плану ("конфликт двух источников порождает явный вопрос с обоими источниками") этим полностью покрывается; более глубокий семантический анализ конфликтов — не обязательное расширение прямо сейчас, а сознательно отложенная возможность.

### Backend: сборка портов вынесена в общий модуль

И запуск новой сессии (`POST /sessions`), и возобновление после ответа на вопрос (`POST /questions/:id/answer`) собирают один и тот же набор адаптеров (confluence, репозиторий, LLM, change engine) из одних и тех же секретов проекта. Раньше эта сборка (~15 строк с проверками) жила только в `sessions.ts`; вынесена в `apps/server/src/orchestrator-ports.ts` (`buildOrchestratorPorts`), возвращающую строго типизированный `FullOrchestratorPorts` (все поля обязательны, в отличие от `OrchestratorPorts`, где LLM-зависимые поля опциональны ради тестируемости стадий 1-5 без AI provider). Не рефакторинг ради рефакторинга — без него пришлось бы либо дублировать эти проверки во втором роуте, либо экспортировать `sessions.ts`-приватную функцию с менее подходящим именем.

### Frontend: гейт-пауза корректно завершает SSE-соединение

SSE-эндпоинт (`GET /sessions/:id/events`) и раньше завершал соединение сразу, если сессия уже была `completed`/`failed` на момент подключения. Добавлено то же самое для `paused-for-user` — дальше по этому соединению ничего не произойдёт, пока пользователь не ответит на вопрос через отдельный HTTP-роут, а не через тот же стрим. `SessionEvent` получил новый тип `'paused'` (вместо того чтобы всегда публиковать `'completed'` независимо от реального исхода — раньше этот шаг был этой мелкой неточностью, было не отличить в логике событий паузу от настоящего завершения, хотя по факту SSE-роут обрабатывал их одинаково). После ответа на последний открытый вопрос `AnalysisPage` открывает новый `EventSource` (инкрементом `connectionAttempt` в зависимостях `useEffect`) — то же самое соединение переиспользовать нельзя, оно уже закрыто сервером на паузе.

### Что реализовано и как проверено

- **`packages/core-pipeline`**: стадии `ambiguity-detection` (9) и `user-clarification` (10, гейт), `PipelineStageDef.isGate`, `computePendingQuestionIds`, доработанный `PipelineOrchestrator.run()` (пауза на гейте + корректное закрытие статуса, когда гейт стал done между вызовами). 2 новых теста в `orchestrator.test.ts`: полный прогон без вопросов (ничего не разрешать — 9 стадий проходятся за один вызов), и полный цикл пауза → имитация ответа → повторный `run()` → `completed`.
- **`apps/server`**: `orchestrator-ports.ts` (общая сборка портов), `routes/questions.ts` (`POST /sessions/:id/questions/:questionId/answer` — валидирует, что вопрос ещё открыт, требует ответ ИЛИ явный "не знаю"/"отложить", пересчитывает `pendingQuestionIds`, автоматически возобновляет pipeline через `runSessionInBackground`, когда открытых вопросов больше нет). `sessions.ts` использует общую сборку портов; `SessionView` получил поле `questions`.
- **Frontend**: `components/QuestionCard.tsx` (карточка вопроса — варианты, свободный текст, "Не знаю"/"Отложить" как явные отдельные действия, не подмешанные в обычный ответ), `AnalysisPage.tsx` — два новых пункта чеклиста, отдельная жёлтая иконка "?" для паузы (не спутать с обычным "выполняется"), автоматическое переподключение SSE после ответа на последний вопрос.
- **Живая браузерная проверка**: фейковый Confluence с двумя намеренно не связанными с существующей моделью требованиями (Loyalty Points Service, Fraud Detection Module) → pipeline дошёл до стадии "Выявление неоднозначностей" → корректно поставился на паузу на "Уточнения от вас" с жёлтым индикатором → отрендерены 2 карточки вопросов с правильными вариантами ("Да, это новый элемент" / "Нет, это существующий") → ответ на первый вопрос через выбор варианта (счётчик "нужно уточнений" корректно уменьшился 2→1) → ответ на второй через "Не знаю" → pipeline автоматически возобновился и дошёл до "Готово" без дополнительных действий пользователя. Оба пути entity-matching отработали корректно и по-разному: для одного требования (без общих слов с графом вообще) LLM не вызывался совсем (0 confidence сразу), для другого (случайно пересекается по слову "service") — вызвался judge и осознанно вернул низкую уверенность — оба случая одинаково честно привели к вопросу, а не к скрытому решению.

### Осознанно не сделано в этом заходе

- **Семантическое (содержательное) разрешение конфликтов через LLM** — `resolveConflicts` остаётся чисто структурным (общий целевой элемент), как и в Milestone 6. Настоящий LLM-анализ "эти два источника противоречат друг другу по смыслу" — не требуется текущим DoD и не реализован, чтобы не расширять milestone за его границы.
- **Экран истории вопросов / отдельный `GET /questions`** — вопросы отдаются как часть `SessionView` (уже опрашиваемого `AnalysisPage`), отдельный эндпоинт не заведён, потому что второго потребителя для него пока нет.
- **"Regenerate" вопроса или пересчёт ambiguity-detection после ответа** — вне рамок: ответы влияют на дальнейшие стадии (Proposal Generation, Milestone 8), а не переигрывают саму стадию 9 заново.

## Milestone 8 — Proposal Generation + Proposal UI (стадии 11-12)

### Найденный и исправленный баг из Milestone 7: один вопрос вместо N при конфликте группы

При проектировании стадии 11 обнаружилось, что `ambiguity-detection.ts` (Milestone 7) создавал **отдельный** `ClarificationQuestion` для КАЖДОГО кандидата в конфликтующей группе, а не один вопрос на группу — то есть при конфликте трёх требований пользователь увидел бы три раза буквально один и тот же вопрос "несколько требований предлагают изменить один и тот же элемент, как поступить?". Это не только избыточно: стадия 11 не могла бы понять, что три отдельных ответа относятся к ОДНОМУ решению, а не к трём независимым. Исправлено — теперь один `ClarificationQuestion` на группу, `relatedProposalItemIds` содержит id всех кандидатов группы; добавлен отдельный regression-тест (`ambiguity-detection.test.ts`), которого раньше не было вовсе (стадия проверялась только косвенно через `orchestrator.test.ts`).

### Более серьёзная находка: `npm test --workspaces` тихо не запускал часть тестов из-за неэкранированного glob

Скрипт `"test": "tsx --test src/**/*.test.ts"` (без кавычек) во всех 13 пакетах с тестами полагался на то, что shell либо развернёт `**` рекурсивно, либо (если совпадений нет) передаст паттерн `tsx` буквально, а тот уже сам обработает `**` правильно через свою реализацию `node:test`. До этого момента это работало случайно: пока в `core-pipeline` был только один тестовый файл прямо в `src/` (без вложенных `.test.ts`), паттерн не находил совпадений в `sh` (shell, которым npm реально исполняет `scripts`, использует bash/dash без `globstar` — там `**` ведёт себя как обычный `*`, то есть требует РОВНО один уровень вложенности) — и передавался `tsx` буквально, где уже нормально раскрывался рекурсивно. Как только в этой сессии появился `stages/ambiguity-detection.test.ts` (вложенный на один уровень), shell нашёл частичное совпадение (только этот файл) и подставил его как явный аргумент — `orchestrator.test.ts` (лежащий прямо в `src/`, ноль уровней вложенности) молча выпал из прогона, причём БЕЗ ЛЮБОЙ ошибки или предупреждения: `npm test --workspaces --if-present` и, соответственно, CI продолжали как ни в чём не бывало показывать «всё зелено», просто не запуская добрую половину тестов этого пакета.

Обнаружено случайно, при проверке нового `ambiguity-detection.test.ts` — итоговое число тестов `core-pipeline` в общем прогоне (3) оказалось подозрительно меньше ожидаемого (8: 5 из `orchestrator.test.ts` + 3 новых). Если бы не эта случайная сверка чисел, регресс в самом архитектурно рискованном компоненте проекта (стейт-машина оркестратора) мог бы месяцами не покрываться CI, оставаясь незамеченным. **Исправлено сразу и системно, а не только в `core-pipeline`**: во всех 13 `package.json` glob-паттерн взят в кавычки (`tsx --test 'src/**/*.test.ts'`) — теперь shell никогда не пытается его раскрыть, паттерн всегда доходит до `tsx`/`node:test` буквально и рекурсивно, независимо от того, сколько файлов и на какой глубине существует. Это тот случай, когда стоило исправить превентивно везде, а не только там, где баг уже проявился — тот же паттерн неминуемо повторился бы в любом другом пакете, как только у него появился бы второй тестовый файл на другой глубине.

### Дизайн: гейт User Review (12) — то же расширение idiom, что и User Clarification (Milestone 7)

`user-review` использует уже существующий механизм `PipelineStageDef.isGate` (Milestone 7) без единого изменения в самом оркестраторе — только `isDone`, специфичный для этой стадии: пропускает дальше, только когда КАЖДЫЙ `ProposalItem.decision` — `approved`, `rejected` или `edited` (не `pending`, не `regenerate-requested`). Единственное изменение в `orchestrator.ts` — синхронизация `session.questions`/`session.proposalId` с соответствующими полями `stageOutputs` внутри `advance()`, а не только в роуте ответа. Это тоже исправление бага из Milestone 7: `session.questions` раньше синхронизировался ТОЛЬКО при ответе на вопрос, а не сразу после того, как `ambiguity-detection` их посчитал — то есть между стадией 9 и первым ответом пользователя `session.questions` показывал пустой список, даже когда `stageOutputs.ambiguities` уже был непустым. Обнаружено при проектировании того же самого механизма для `proposalId` — задав себе вопрос "а где я буду синхронизировать это поле", нашёл, что для `questions` этот вопрос был улажен только наполовину.

### Честное потребление решений стадий 9-10 в Proposal Generation — не просто "сгенерировать и забыть"

Ключевое опасение при проектировании: если `LLMProposalGenerator` игнорирует ответы на `ClarificationQuestion`, вся работа стадий 9-10 (Milestone 7) становится собранной, но бесполезной информацией. Реализовано три честных сценария:
- **"merge" на вопросе о конфликте** → несколько `ArchitectureChangeCandidate` объединяются в ОДИН `ProposalItem` (первый кандидат группы отдаёт свой id, источники — объединение источников всех кандидатов группы, без дублей) — один вызов LLM на группу, а не по одному на кандидата.
- **"reject-match" на вопросе о низкой уверенности** → кандидат трактуется как новый элемент (`modified-element`→`new-element`, `targetElementId` очищается), а не как подтверждённое, но на деле отвергнутое сопоставление.
- **"не знаю"/"отложить"** → решение AI используется как есть (это осознанный, а не забытый случай), но факт неподтверждённости явно попадает в `sources` (`kind: 'user-answer'`) — не выдаётся молча за подтверждённый факт (ФТ14).

Все четыре сценария закреплены golden-тестами в `packages/proposal-generator` (включая regression-тест на то, что промпт содержит уже принятые тип/target, а не просит модель придумать их заново).

### `ContextBuilder` наконец подключён — ровно там, где и предполагалось в Milestone 6/7

`LLMProposalGenerator` — первый реальный потребитель `ContextBuilder` (собран в Milestone 6): для каждого предложения строится BFS-срез графа вокруг целевого элемента (если он есть) с обрезкой по токен-бюджету, применимыми Architecture Rules и knowledge-чанками — вместо передачи модели всего графа целиком.

### Осознанная граница простоты: "Regenerate" на объединённом (merged) item откатывает merge

Точечная регенерация (`POST /proposal/items/:itemId/regenerate`) ищет исходного кандидата по `candidate.id === itemId`. Если item был результатом "merge" двух кандидатов, у него остался только id ПЕРВОГО — регенерация не восстанавливает исходную группу, а пересобирает item заново с нуля как одиночный кандидат, теряя объединение. Это осознанная, документированная граница простоты: полноценное решение потребовало бы либо хранить состав merge-группы отдельным полем в `ProposalItem` (которого сейчас нет в модели), либо каждый раз пересчитывать `generate()` для ВСЕХ кандидатов заново ради одного item (дорого и не "точечно", как того требует план). Пользователь, которому важно сохранить merge при регенерации, может вместо этого использовать "Изменить" (ручную правку без обращения к LLM).

### Что реализовано и как проверено

- **`packages/core-domain`**: новый порт `ProposalGenerator`.
- **`packages/proposal-generator`** (новый пакет): `LLMProposalGenerator` — merge-группировка по ответу "merge", учёт "reject-match", сборка контекста через `ContextBuilder`, один вызов LLM на item/группу. 8 golden-тестов.
- **`packages/core-pipeline`**: стадии `proposal-generation` (11) и `user-review` (12, гейт); исправлен баг группировки конфликтных вопросов в `ambiguity-detection.ts` (+3 новых теста); `advance()` теперь синхронизирует `session.questions`/`session.proposalId`; обновлены/расширены тесты `orchestrator.test.ts` под 12 стадий.
- **Инфраструктурный фикс**: glob в `test`-скрипте заквочен во всех 13 пакетах — `npm test --workspaces`/CI теперь гарантированно запускают все `*.test.ts` файлы независимо от вложенности.
- **Backend**: `apps/server/src/routes/proposals.ts` — `POST .../proposal/items/:id/decision` (approved/rejected/edited, с ручной правкой кода при edited) и `POST .../proposal/items/:id/regenerate`; оба переиспользуют `buildOrchestratorPorts`/`runSessionInBackground` из Milestone 7. `SessionView` получил поле `proposal`.
- **Frontend**: `components/ProposalItemCard.tsx` (Explanation целиком на виду — ФТ13, источники, черновик LikeC4, 4 действия), `pages/ProposalPage.tsx` (новый экран, отдельный от Analysis — как и предполагает список экранов в плане), `AnalysisPage.tsx` — 2 новых пункта чеклиста + баннер-ссылка на Proposal при паузе на user-review + сводка принятых/отклонённых/отредактированных решений на итоговом экране.
- **Живая браузерная проверка**: полный прогон 12 стадий (fake Confluence + fake OpenAI, сценарий из Milestone 6 — Refund Service новый + Order Service доработка) → пауза на "Проверка предложений вами" с 2 карточками → проверены все 4 действия (Принять, Изменить с ручной правкой кода и комментарием, Перегенерировать — с реальным повторным вызовом LLM и сбросом решения в "Ожидает решения", Отклонить) → после того как решение принято по всем пунктам, pipeline автоматически возобновился и дошёл до "Готово" с корректной сводкой решений.

### Осознанно не сделано в этом заходе

- **UI для просмотра истории Proposal вне текущей сессии** — читается только через уже существующий `SessionView`, отдельного `GET /proposal` эндпоинта нет за отсутствием второго потребителя.
- **Разрешение "reject-new" (пользователь считает элемент существующим, но не указал каким)** — как и в Milestone 7, честно сворачивается в `assumptions`/`sources`, не пытается угадать целевой элемент — это решение остаётся за человеком на экране Proposal (Reject/Edit).

## Milestone 9 — LikeC4 Generation + двухуровневая валидация + Repair (стадии 13-16)

### Самокоррекция: стадия 13 обошлась БЕЗ повторного вызова LLM, вопреки собственному прогнозу выше

В конце Milestone 8 я написал, что стадия 13 "обязана перепроверить и, скорее всего, перегенерировать" `proposedLikeC4Code`. При реализации оказалось, что это не так: `ProposalItem.proposedLikeC4Code` уже содержит финальный текст — написанный AI на стадии 11 и одобренный человеком (или написанный человеком вручную через "Изменить" на стадии 12). Повторно вызывать LLM здесь означало бы тихо переписывать то, что человек только что одобрил или сам отредактировал — прямое нарушение смысла User Review. Стадия 13 в итоге получилась полностью механической (`assembleGeneratedFiles` — чистая функция, без единого обращения к LLM): она только размещает уже готовый текст в правильном месте гипотетического слитого состояния файлов, используя `ArchitectureElement.sourceRef` (id/файл/диапазон строк), который граф архитектуры ведёт с Milestone 1 специально "для diff/repair" — именно для этого момента.

### Хорошая новость: технический валидатор (Level 1) был готов с Milestone 1

`LikeC4Validator.validateTechnical(files)` уже существовал как порт и как рабочая реализация (`LikeC4NpmValidator`, через временный workspace и настоящий `likec4` npm-пакет) — просто не был частью `OrchestratorPorts` до этого момента, потому что не было стадии-потребителя. Стадия 14 практически не потребовала новой инфраструктуры — только подключить уже готовый, уже протестированный порт.

### Найденный и исправленный пробел в модели данных: `validationResult` не мог быть заполнен по частям

`PipelineState.stageOutputs.validationResult: { technical: TechnicalValidationResult; architectural: ArchitecturalValidationResult }` был заведён ещё в Milestone 0 с обоими полями обязательными. Но стадия 14 (Validation) и стадия 15 (Architecture Review) — это две РАЗНЫЕ стадии, которые пишут в это поле по отдельности, и между их выполнением `architectural` объективно ещё не существует. С обязательными полями стадия 14 не могла честно записать "technical посчитан, architectural — ещё нет", не выдумывая для него заглушку. Исправлено — оба подполя стали опциональными (`technical?`, `architectural?`); каждая стадия проверяет `isDone` только по своему подполю.

### Новый rule-engine (Level 2) — сознательно только детерминированный, без LLM

Новый пакет `packages/architecture-reviewer` (`RuleBasedArchitecturalReviewer`) реализует три проверки без единого обращения к LLM:
- обязательные metadata-поля (`ArchitectureRule.requiredMetadata`);
- naming convention по regex (`ArchitectureRule.namingConventionPattern`);
- лексические дубликаты — новый элемент текстуально похож на уже существующий (та же jaccard-эвристика, что и в `lexicalCandidates` из Milestone 6, но независимая небольшая реализация: подгонять чужой API под другую предметную область показалось менее честным, чем 10 строк своего кода).

LLM-assisted проверки "на смысловые вещи", упомянутые в плане для Level 2, в этом пакете сознательно не реализованы — детерминированных проверок достаточно, чтобы DoD milestone'а ("намеренно проблемный тест-кейс либо самовосстанавливается, либо корректно останавливается") выполнялся честно, а разрастание на нечётко специфицированный "смысловой" анализ отложено на будущее.

Находки дубликатов всегда `severity: 'should'`, никогда `'must'` — это эвристика с false positive, и её роль — подсказать человеку, а не автоматически блокировать Apply или запускать repair.

### Ключевое архитектурное ограничение: repair — это цикл ВНУТРИ одного `run()`, а не переход между стадиями

`PipelineOrchestrator.run()` проходит `STAGES` строго по порядку один раз за вызов; он не умеет "вернуться" к стадии 14 после стадии 16. Если бы `repairStage.run()` просто чинил один item и возвращал управление, оркестратор молча продолжил бы к следующей стадии, даже если проблема осталась. Поэтому `repairStage.run()` — единственная стадия с циклом `while` внутри себя: чинит только item'ы, чьи файлы/находки реально сломаны, пересобирает `generatedFiles` тем же `assembleGeneratedFiles`, валидирует заново (по-настоящему вызывая `likec4Validator`/`architecturalReviewer`, не имитацию) — и продолжает, пока не останется блокирующих проблем или не закончится `MAX_REPAIR_ATTEMPTS` (2). При исчерпании — не новый статус pipeline, а обычный `throw`, подхваченный уже существующим `fail()` оркестратора (Milestone 5): прогресс сохраняется, `UserFacingError.likelyCause` содержит полный дамп диагностик и находок — тот же механизм, что и у любой другой упавшей стадии, а не специальный случай.

### Живая проверка неожиданно продемонстрировала ОБА сценария DoD — один из них случайно

Первый прогон в браузере (с намеренно сломанным на стадии 11 черновиком — без закрывающей скобки) должен был показать самовосстановление, но показал второй сценарий DoD: repair дважды честно пытался (мой фейковый сервер "чинил" скобку, но забыл обязательную обёртку `model { }` вокруг элемента — настоящий парсер `likec4` справедливо не принял и это), и pipeline корректно остановился с explicit-сообщением: `Не удалось исправить проблемы валидации за 2 попытки(-ок)` + полный текст диагностики `Expecting token of type 'EOF' but found 'service'`. Это не баг production-кода — это баг тестовых данных фейкового сервера, но результат honestly ценнее: он доказал сценарий "корректно останавливается" на **настоящем** парсере `likec4`, а не на моей собственной идее о том, как он должен себя вести. Поправил фейковый сервер (обернул исправленный код в `model { }`) и повторил прогон — на этот раз repair починил с первой попытки, pipeline дошёл до "Готово" с 0 диагностик и 0 находок. Оба сценария DoD подтверждены на реальном `likec4Validator`, не на тестовых дублёрах.

### Что реализовано и как проверено

- **`packages/core-domain`**: новый порт `ArchitecturalReviewer`; `ProposalGenerator` расширен методом `repair()`; `validationResult` — оба подполя опциональны.
- **`packages/architecture-reviewer`** (новый пакет): `RuleBasedArchitecturalReviewer` — метаданные, naming convention, лексические дубликаты. 7 тестов.
- **`packages/proposal-generator`**: `LLMProposalGenerator.repair()` — точечно чинит один item по diagnostics/findings, сохраняя id/type/target; правка явно попадает в `explanation.assumptions`, а не скрывается. +2 теста.
- **`packages/core-pipeline`**: `assembleGeneratedFiles` (чистая функция сборки гипотетического слитого состояния файлов — новые элементы в отдельные файлы, modified-* точечно заменяют строки по `sourceRef`) + 7 тестов; стадии `likec4-generation` (13), `validation` (14), `architecture-review` (15), `repair` (16, с внутренним циклом) + 5 тестов на repair (самовосстановление, исчерпание попыток, три варианта `isDone`); `orchestrator.test.ts` расширен до полного прогона всех 16 стадий.
- **Backend**: `composition-root.ts`/`orchestrator-ports.ts` подключают `likec4Validator` (существовал с Milestone 1, просто не был частью pipeline ports) и `architecturalReviewer`; `SessionView.summary` — счётчики сгенерированных файлов/диагностик/находок/попыток репейра.
- **Frontend**: 4 новых пункта чеклиста на `AnalysisPage`, сводка по файлам/диагностикам/repair на итоговом экране.
- **Живая браузерная проверка** (см. выше) — оба сценария DoD подтверждены на реальном `likec4` npm-пакете, не на дублёрах: самовосстановление за одну попытку и явная, содержательная остановка при исчерпании попыток.

### Осознанно не сделано в этом заходе

- **LLM-assisted "смысловые" проверки Level 2** — детерминированного rule-engine достаточно для DoD; отложено.
- **Восстановление дубликатов из "should"-находок** — они информационные, Proposal Review (Reject/Edit) остаётся местом, где человек решает такие вопросы.
- **UI для просмотра `repairAttempts`/сравнения кода до и после чинки** — сводка на `AnalysisPage` показывает только счётчик попыток; подробный лог правок пока доступен только через `UserFacingError` при неудаче или напрямую в данных сессии.

## Milestone 10 — Diff + Preview + Apply/Rollback/History (стадии 17-19)

### Домен уже был спроектирован под это заранее — почти без сюрпризов

`PipelineStageId` уже включал `'diff' | 'preview' | 'apply'`, `stageOutputs` уже резервировал `diff`/`previewViews`, `ApplyResult` уже был описан на `SessionRecord`, `SnapshotStore`/`FsSnapshotStore` существовали с Milestone 2, `renderViewsPreview` — с Milestone 1. Единственный реальный пробел в модели данных: `ApplyResult` был описан только как top-level поле `SessionRecord`, а не внутри `stageOutputs` — но гейт-стадия проверяет готовность именно через `isDone(stageOutputs)`, который не видит остальную сессию. Исправлено тем же способом, что и `validationResult` в Milestone 9: `applyResult?: ApplyResult` переехал внутрь `stageOutputs` как источник истины, top-level поле осталось зеркалом, синхронизируется в `advance()`.

### Технический спайк по рендереру диаграмм: статический анализ типов соврал, живая проверка поправила

По документации типов `likec4/react` выглядело так, будто `LikeC4Diagram` принимает `LayoutedView` напрямую пропом и не требует контекст-провайдера для базового интерактивного режима — `LikeC4ModelProvider` в типах помечен нужным только для продвинутых фич (cross-view navigation, relationship browser). На основании этого бэкенд был расширен: `likec4-validator.ts`'s `renderViewsPreview` стал вызывать `instance.diagrams()` (существующий метод `LikeC4.fromWorkspace()`, с комментарием в самой библиотеке "Used in React components") параллельно с уже существующим SVG-путём, отдавая `{ viewId, svg, layoutData }`.

Живая браузерная проверка немедленно опровергла этот вывод: `<LikeC4Diagram view={layoutData} />` без обёртки в `LikeC4ModelProvider` падает в рантайме с `Error: LikeC4Model not found. Make sure you have LikeC4ModelProvider.` — типы не отражают это требование, оно проверяется только во время исполнения. Полноценная клиентская `LikeC4Model` потребовала бы либо парсинга всего проекта в браузере через `@likec4/core`'s model builder, либо отдельного backend-эндпоинта, отдающего сериализованный dump модели — заметно больший объём работы, чем оправдано для MVP одного экрана Preview.

Это ровно тот сценарий, который план предусмотрел заранее: «если встраивание... окажется несоразмерно сложным — fallback на серверный экспорт в SVG + zoom/pan обёртка». Откатился на этот путь: `PreviewPage` рендерит `svg` как `<img>` внутри `overflow-auto` контейнера с кнопками +/− (шаги масштаба 50%-300%) — простая, но рабочая zoom/pan обёртка без сторонней библиотеки. Зависимости `likec4`/`@likec4/core`, добавленные в `apps/web` для интерактивного пути, убраны обратно — код, который их использовал бы, не остался в дереве. `layoutData` при этом НЕ убран из бэкенда/домена/тестов — данные корректны, дёшево посчитаны тем же вызовом, и пригодятся, если решим вернуться к интерактивному рендерингу отдельным заходом (потребует `LikeC4ModelProvider` — уже задокументированная, а не забытая, причина отката).

### Найденный и исправленный пробел в `RepositoryAdapter`: Rollback не удалял новые файлы

Первый прогон live-проверки Apply → Rollback показал реальный баг: `SnapshotStore.restore()` возвращает только файлы, которые существовали НА МОМЕНТ снэпшота — если Apply создал новый файл (`generated/refund-service.c4`), а `RepositoryAdapter.writeFiles()` умеет только писать/перезаписывать, но никогда не удаляет, то после "отката" новый файл оставался на диске осиротевшим. Формально `model.c4` совпадал побайтово с исходным, но репозиторий в целом — нет: `find` на директории показывал лишний файл. Это не было замечено при code review до живой проверки — юнит-тесты снэпшота проверяли `restore()` изолированно (RepositoryFile[] совпадает с тем, что было сохранено), а не end-to-end состояние файловой системы после полного цикла Apply→Rollback.

Исправлено добавлением `RepositoryAdapter.deleteFiles(paths: string[]): Promise<void>` в порт (реализовано в `LocalRepositoryAdapter` через `rm(..., { force: true })`, и как явный "не поддерживается" в `BitbucketServerAdapter`, симметрично `writeFiles`). Роут восстановления снэпшота (`history.ts`) теперь дополнительно вычисляет разницу между текущими файлами на диске и файлами в снэпшоте и удаляет всё, чего в снэпшоте не было. Заодно `apply.ts` начал честно обрабатывать `changeType: 'deleted'` записи diff (раньше молча отфильтровывались — ветка, которую `computeFileDiff` теоретически может произвести, но которая раньше никуда не вела).

### Риск №6 (конкурентная запись) — все три меры, все проверены живьём

- **Snapshot перед каждым Apply** — `SnapshotStore.create` вызывается для полного текущего набора файлов с диска (не для `stageOutputs.existingFiles`, которые могли устареть) непосредственно перед записью.
- **Hash-check** — перед записью сравнивается sha256 текущего содержимого затронутых файлов с sha256 того, что было на момент анализа (`stageOutputs.existingFiles`); для новых файлов проверяется, что путь всё ещё свободен. Живая проверка: положил на диск "чужой" файл по тому пути, куда должен был попасть сгенерированный `generated/refund-service.c4`, нажал Apply — получил явную ошибку `Файлы изменились на диске с начала анализа` со списком путей, чужой файл остался нетронутым (Apply не был запущен вовсе, не то что не перезаписал — hash-check стоит ДО snapshot/записи).
- **Project-level mutex** — `AppContainer.withProjectLock`, простая in-process цепочка promise'ов по `projectId`, используется и Apply, и Restore. Однопроцессный локальный сервер — ОС-уровневый файловый лок был бы избыточен.

### Архитектурное решение: роут Apply не проходит через `buildOrchestratorPorts`

В отличие от `questions.ts`/`proposals.ts` (которые возобновляют pipeline через `buildOrchestratorPorts`/`runSessionInBackground`), `apply.ts` строит `RepositoryAdapter` напрямую из `AppContainer` и после успешной записи сам выставляет `pipelineState.status: 'completed'`, не вызывая оркестратор целиком. Apply — последняя стадия и физически не нуждается ни в LLM, ни в Confluence; требовать их рабочими только чтобы записать уже сгенерированный и провалидированный код было бы лишней, не связанной с Apply точкой отказа (например, если ключ AI-провайдера протух уже после анализа — Apply всё равно должен сработать).

### Побочный рефакторинг: `hasBlockingValidationIssues` — было три копии, стала одна

Логика Apply gate ("Level 1 без ошибок и нет неразрешённых must-findings") оказалась продублирована: приватная версия внутри `repair.ts` (используется в цикле, где оба уровня валидации гарантированно посчитаны), инлайн-версия в `sessions.ts` (для `SessionSummary`, где уровни могут быть ещё не посчитаны — `undefined`), и нужна была третья копия в новом `apply.ts` (серверная проверка гейта, не только по кнопке на фронтенде). Вместо третьей копии вынес общую `hasBlockingValidationIssues(validationResult): boolean | undefined` в `packages/core-pipeline/src/validation-gate.ts`, покрыл 6 тестами все комбинации (technical/architectural посчитаны или нет, ok/not-ok, must/should), и `repair.ts`/`sessions.ts` тоже переведены на неё — три места, которые рисковали разойтись, стали одним.

### Наблюдение: "Apply задизейблен при непройденной валидации" — структурная гарантия, а не только кнопка

При ближайшем рассмотрении оказалось, что достичь гейта `apply` с `hasBlockingValidationIssues !== false` в принципе невозможно через обычный поток pipeline: `repairStage.isDone` (стадия 16) буквально и есть условие "нет блокирующих проблем", а стадии 17-18 (diff/preview) не гейты и выполняются автоматически сразу за ним — то есть к моменту, когда pipeline впервые останавливается на `apply`, валидация гарантированно чиста по построению; если бы она не была чиста, `repairStage.run()` бросил бы исключение раньше, и сессия ушла бы в `failed`, а не дошла бы до `apply` вовсе. И кнопка на `ApplyPage`, и серверная проверка в `apply.ts` — тем не менее оставлены как есть: defense-in-depth на случай будущего рефакторинга оркестратора, а не декоративный код. DoD-формулировка плана выполнена сильнее буквального прочтения — это не "иногда задизейбленная кнопка", а структурная невозможность достичь Apply в невалидном состоянии, подкреплённая тем же UI/серверным чек-листом как последний рубеж.

### Что реализовано и как проверено

- **`packages/core-domain`**: `ApplyResult` внутри `stageOutputs`; `RepositoryAdapter.deleteFiles`.
- **`packages/core-pipeline`**: `computeFileDiff` (стадия 17, 5 тестов) + стадии `diff`/`preview`/`apply` (apply — гейт, `run()` не вызывается); `validation-gate.ts` (6 тестов), переиспользован в `repair.ts`; `orchestrator.test.ts` расширен до полного прогона всех 19 стадий (пауза на `apply`, симуляция роута, `completed`).
- **`packages/likec4-adapter`**: `renderViewsPreview` возвращает `layoutData` (plain-JSON `LayoutedView`) вдобавок к `svg`; regression-тест на JSON round-trip.
- **`packages/repo-local-adapter`/`repo-bitbucket-adapter`**: `deleteFiles` (реализация + "не поддерживается в MVP" соответственно), тесты на оба.
- **Backend**: новые роуты `apply.ts` (hash-check, snapshot, mutex, атомарная запись, апдейт статуса без полного оркестратора) и `history.ts` (список сессий+снэпшотов, восстановление с удалением осиротевших файлов, session-scoped `/rollback`); `composition-root.ts` — `withProjectLock`; `sessions.ts` — `diff`/`previewViews`/`applyResult` в `SessionView`.
- **Frontend**: `DiffPage` (split-view по файлам), `PreviewPage` (SVG + zoom-обёртка, не интерактивный React-компонент — см. спайк выше), `ApplyPage` (сводка, disabled-кнопка, Rollback), `HistoryPage` (сессии + снэпшоты + Restore); `AnalysisPage` — 3 новых пункта чеклиста и карточка-переход на Apply.
- **Живая браузерная проверка** (обязательна для фронтенд-изменений) — три отдельных прогона на тестовом локальном LikeC4-проекте с фейковыми Confluence/OpenAI: (1) полный happy path New Task → Proposal → Approve → все стадии до `apply` автоматически → Diff (виден новый файл с реальным содержимым) → Preview (SVG-диаграмма с зумом) → Apply (файл реально появился на диске, `model.c4` не тронут) → Rollback (файлы вернулись byte-for-byte к исходным, включая удаление нового файла — после того как это же обнажило и позволило исправить баг с осиротевшими файлами, см. выше); (2) hash-check конфликт — положил "чужой" файл по пути будущего сгенерированного файла, Apply корректно отказал с explicit-сообщением, ничего не перезаписав; (3) по пути обнаружен и исправлен баг в собственном тестовом фейк-сервере (draft без обязательной обёртки `model { }` вокруг top-level `service` — не production-баг, но живой прогон именно поэтому и обязателен: он поймал это через настоящий `likec4Validator`, а не через мою собственную идею о том, что должно быть валидно).

### Осознанно не сделано в этом заходе

- **Интерактивный React-рендерер (`LikeC4Diagram` + `LikeC4ModelProvider`)** — статический анализ типов недооценил объём работы; отложено до отдельного захода, если понадобится (см. спайк выше). `layoutData` уже считается и отдаётся с бэкенда — задел для этого остался, а не выброшен.
- **Частичный Apply с выбором подмножества items на экране Apply** — по плану "выбранные items" — это уже принятые на стадии 12 решения (approved/edited), не новый UI-выбор здесь.
- **Снэпшот перед Rollback (`'pre-rollback'`)** — по плану снэпшот создаётся только перед Apply; не расширял модель сверх этого.
- **OS-уровневый файловый лок** — in-process mutex достаточен для однопроцессного локального инструмента.

## Milestone 11 — UX polish: Help System, Onboarding, User Documentation

### Отклонение от архитектурной диаграммы: `ui-kit` — директория внутри `apps/web`, не отдельный npm-пакет

План рисует `/ui-kit` как top-level директорию монорепо, но ни один из существующих `packages/*` не является frontend-пакетом — все они backend/domain-код без build-шага, потребляемый напрямую через `tsx`/`node`. Завести `packages/ui-kit` с React-компонентами означало бы первый в проекте кросс-пакетный TSX-импорт в Vite без отдельного build-шага — риск (нужно было бы проверять, что Vite корректно резолвит TSX соседнего workspace-пакета) без реальной выгоды: код помощи/онбординга нужен только `apps/web`, никто другой его не переиспользует. Решение — `apps/web/src/ui-kit/help` и `apps/web/src/ui-kit/onboarding`: путь `ui-kit/help/content`, буквально процитированный в плане, сохранён один-в-один, просто корень — `apps/web/src/`, а не repo root.

### "5 уровней" — прогрессивное раскрытие одной записи, а не 5 разных мест

Формулировка плана («`HelpTopic` записи: label / inline description / tooltip / context help / doc link») прочитана как один объект с пятью полями, раскрывающимися по нарастающей: `label` (имя в списке Help Center) → `inlineDescription` (то же самое, что уже было на экранах как обычный `text-xs` helper-текст под полем, — эти существующие подсказки НЕ выброшены и не переписаны на реестр, они и есть уровень 2) → `tooltip`/`contextHelp` (наведение/клик на `<HelpAnchor>`) → `docLink` (переход в Help Center). Один компонент `HelpAnchor` обслуживает уровни 3-5; уровни 1-2 показываются либо в самом Help Center (список тем), либо уже существующим на экране текстом.

### Onboarding: без DOM-spotlight, декларативный список шагов поверх тех же данных

13 шагов (`ui-kit/onboarding/steps.ts`) один в один покрывают путь пользователя по всем 13 реальным экранам: Welcome → Create Project → Confluence → AI-провайдер → Architecture Rules → New Task → Analysis → Questions → Proposal → Diff+Preview → Apply → Rollback → History. Осознанно не стал строить подсветку реальных DOM-элементов (measuring positions, порталы, resize observers) — простая пошаговая панель с текстом и кнопкой "Перейти" на нужный маршрут полностью покрывает цель "познакомить с основными экранами" для локального однопользовательского инструмента, не утяжеляя кодовую базу инфраструктурой, которая не была явно запрошена. Состояние — `localStorage` (`onboarding-dismissed`), без серверной персистентности: она здесь не нужна и не была бы использована (один пользователь, один браузер).

Номер шага ("Шаг X из N") сознательно НЕ захардкожен в тексте каждого шага, а вычисляется панелью по индексу массива — на предыдущей итерации черновика я сначала пронумеровал шаги прямо в `title` ("Шаг 1 — …", "Шаг 2 — …") и почти сразу поймал у себя же рассинхронизацию: массив получился на 14 записей вместо 13 (лишний закрывающий шаг "Готово!"), и после того как я его убрал, все номера после него сдвинулись бы, если бы были захардкожены текстом.

### Live-проверка: инструмент показывал пустые скриншоты — оказалось не багом приложения

При проверке перехода `HelpAnchor` → Help Center → якорь конкретного раздела документации скриншоты Browser pane стабильно приходили полностью пустыми (светло-серый фон, ни одного пикселя контента) на нескольких разных scroll-позициях подряд. Углублённая диагностика через `getBoundingClientRect`/`getComputedStyle`/`elementsFromPoint` (в обход скриншотов) показала, что DOM, computed-стили, позиционирование и accessibility-дерево — все корректны: нужный `<h2>` находится строго внутри вьюпорта, тёмным текстом на светлом фоне, ничего не перекрыто. Отдельный вызов `tabs_context` явно подтвердил причину: `"The Browser pane is currently hidden"` — панель на стороне пользователя была свёрнута/неактивна, и скриншот скрытой панели тихо возвращает пустое изображение вместо ошибки (в отличие от `scroll`/`hover`, которые в этой ситуации честно бросают timeout с объяснением). Дальнейшая проверка велась через `get_page_text`/`find`/`read_page`/`javascript_tool` (не зависят от видимости панели) — все сценарии (автопоказ онбординга, переходы по шагам, поповер `HelpAnchor`, переход по `docLink`, `helpTopicId` → "Подробнее →" в `ErrorState`, persist/restart флага) подтверждены именно так.

- **`scripts/check-help-completeness.mjs`**: текстовое сканирование (без импорта `content.ts` как модуля — файл на TS, отдельного build-шага у `apps/web` в CI нет) `apps/web/src/pages/*.tsx` — каждый экран (кроме самого Help Center) содержит `<HelpAnchor>`, каждый использованный `topicId` существует в реестре, каждый `docLink` указывает на реальный файл в `docs/user-guide/`. Подключён в `lint`: `"eslint . && node scripts/check-help-completeness.mjs"`. Проверено намеренной опечаткой в `topicId` — падает с понятным сообщением, эффект отменён.
- **Живая браузерная проверка**: автопоказ онбординга на чистом `localStorage`, переход по шагам и по маршруту кнопкой "Перейти", `HelpAnchor` (hover/tooltip через `title`, click/поповер с `contextHelp`) на нескольких разных экранах, переход "Подробнее →" в правильный якорь Help Center, реальная ошибка с `helpTopicId` (`sessions.confluence-not-configured` — попытка запустить задачу без Confluence) показывает "Подробнее →" в `ErrorState` с правильной ссылкой, `localStorage`-флаг переживает перезагрузку страницы, "Показать введение снова" в Help Center сбрасывает и перезапускает онбординг.

### Осознанно не сделано в этом заходе

- **DOM-spotlight в onboarding** — см. выше, простой пошаговой панели достаточно для DoD.
- **`helpTopicId` на всех 27 существующих ошибках** — только на 5 наиболее релевантных; остальные (в основном "не найдено"/"невалидный ввод") не выигрывают от ссылки на Help Center.
- **`packages/ui-kit` как отдельный npm-пакет** — см. отклонение от диаграммы выше.
- **Замена существующих инлайн-подсказок (`text-xs text-slate-400`) на данные из реестра** — они уже корректно выполняют роль уровня 2 ("inline description"), переписывать их ради самого факта единого источника не стал: реальной пользы (кроме теоретического DRY) это не давало, а риск визуальной регрессии на уже проверенных экранах — не нулевой.
